# Local-first Personalized Academic Paper Recommendation Agent

This project is a local-first AI agent for personalized academic paper recommendations. It reads a user's Zotero library, collects recent papers from arXiv, ranks candidates locally against the user's research profile, and uses an OpenAI-compatible cloud LLM only for final reasoning, reranking, summaries, and recommendation explanations.

The MVP is designed for an AI Agent competition: the emphasis is a complete, modular, demonstrable agent workflow rather than complex ranking algorithms.

## Architecture

- `app/`: application entry points, configuration loading, and the Streamlit UI.
- `models/`: Pydantic data models shared across agents, connectors, storage, and UI.
- `connectors/`: external data connectors such as Zotero and arXiv.
- `memory/`: local persistence, including SQLite and future vector storage.
- `agents/`: profile, collection, ranking, and digest agents.
- `llm/`: OpenAI-compatible LLM client and prompts.
- `workflows/`: end-to-end daily recommendation workflows.
- `data/`: local runtime data such as SQLite databases and caches.
- `tests/`: test files and smoke checks.

## Local-first Principles

- API keys, Zotero metadata, recommendation history, feedback, and profile memory stay on the user's machine.
- Local code handles Zotero reading, caching, embedding, rough ranking, and feedback memory.
- The cloud LLM receives only the compact information needed for reranking and explanations.
- No developer-hosted server is required.

## Local Database Design

The SQLite database separates papers by business role:

- `user_library_papers`: papers already in the user's own library. The current source is Zotero, and these records are used later by the Profile Agent to infer research interests.
- `candidate_papers`: papers that may be recommended. The current source is arXiv, and future candidate sources can include OpenReview, Semantic Scholar, or Papers With Code.
- `ranking_runs`: one row per module 5 rough-ranking execution, recording its method, embedding model, limits, and result count.
- `local_rankings`: intermediate local rough-ranking results generated by the embedding ranker. Each row belongs to a `ranking_runs` batch through `ranking_run_id` and is labeled by `ranking_method` (`profile` or `library`).
- `user_zotero_paper_embeddings`: cached local embeddings of Zotero abstracts for library-content ranking.
- `arxiv_paper_embeddings`: cached local embeddings of arXiv candidate abstracts for library-content ranking.
- `recommendations`: final user-facing recommendation records generated after LLM reranking or final local fallback; these reference both `candidate_papers` and the source `ranking_runs` batch.
- `feedback`: user feedback that references `candidate_papers`.
- `user_profile`: local user profile snapshots with only the core profile fields: explicit interests, inferred keywords, representative papers, research summary, Zotero paper count, and timestamps.

Older databases may still contain the legacy `papers` table. Running any command that initializes SQLite, such as `python app/main.py --db-smoke-test`, migrates legacy `source='zotero'` rows into `user_library_papers` and legacy `source='arxiv'` rows into `candidate_papers`. The legacy `papers` table is retained to avoid data loss.
Existing unbatched `local_rankings` rows are preserved and grouped into legacy `ranking_runs` by ranking method when the new schema is initialized.

## Module 2 Zotero Connector

Configure Zotero credentials in `.env`:

```bash
ZOTERO_USER_ID=your_zotero_user_id
ZOTERO_API_KEY=your_zotero_api_key
ZOTERO_LIBRARY_TYPE=user
```

Then fetch and save Zotero library items:

```bash
python -m connectors.zotero_connector --max-items 50
```

Expected behavior:

- Without credentials, the command prints a clear configuration error.
- With credentials, the command fetches Zotero items, converts them to the shared `Paper` model, saves them to `data/local.db`, and prints the first few saved paper titles.

## Module 3 arXiv Collector

Configure categories and fetch limits in `.env`:

```bash
ARXIV_CATEGORIES=cs.AI,cs.CL,cs.LG
ARXIV_LOOKBACK_DAYS=3
ARXIV_MAX_RESULTS=50
ARXIV_REQUEST_DELAY_SECONDS=3
ARXIV_NUM_RETRIES=1
```

Fetch and save recent arXiv papers:

```bash
python -m connectors.arxiv_connector --categories cs.AI,cs.CL --lookback-days 3 --max-results 50
```

Expected behavior:

- The command queries arXiv by category.
- The command keeps papers from the configured recent window.
- The command requests only the configured `max_results` page size and uses a polite delay for retries/pagination. If arXiv responds with HTTP 429, wait briefly before retrying rather than repeatedly rerunning the command.
- Saved papers use `source='arxiv'` and can be inspected in `data/local.db`.

## Module 4 Profile Agent

Build and save a local research profile from Zotero library papers:

```bash
python -m agents.profile_agent --max-papers 200 --profile-mode local
```

Expected behavior:

- The agent reads Zotero papers from `user_library_papers`.
- The agent combines `USER_INTEREST_KEYWORDS` with local tag and title/abstract keyword statistics.
- The agent saves a `user_profile` row with explicit interests, inferred keywords, representative papers, and a readable research summary.
- The command works without an LLM API key.
- Use `--profile-mode hybrid` to let an OpenAI-compatible LLM build a structured profile from compressed local signals, with local fallback if the LLM is unavailable.
- Use `--profile-mode llm` to prefer the LLM-built keywords and summary when credentials are configured.

## Module 5 Local Embedding Ranker

Run local rough ranking over candidate papers:

```bash
python -m agents.ranker_agent --ranking-mode profile --candidate-limit 200 --top-n 20
```

Expected behavior:

- The ranker reads the latest `user_profile`.
- The ranker builds profile embedding text at ranking time rather than storing it in `user_profile`.
- The ranker embeds the profile and `candidate_papers`, computes cosine similarity, adds keyword bonuses, filters already finalized recommendations and negative-feedback papers, and saves one `ranking_runs` batch plus its Top N intermediate rows in `local_rankings`.
- The default embedding backend tries `sentence-transformers` with `EMBEDDING_MODEL_NAME`; if the package or local model is unavailable, it falls back to a deterministic local hashing embedding so the MVP still runs offline.

Run time-weighted Zotero abstract content ranking:

```bash
python -m agents.ranker_agent --ranking-mode library --candidate-limit 200 --top-n 20
```

In `library` mode:

- Only Zotero library papers and arXiv candidates with non-empty abstracts participate.
- Zotero papers are ordered by `date_added` descending; missing dates are placed last.
- A recent-interest weight is computed as `1 / (1 + log10(index + 1))` and normalized to sum to `1`.
- Each candidate score is the weighted sum of its abstract cosine similarities to all eligible Zotero abstracts.
- Abstract embeddings are cached locally in `user_zotero_paper_embeddings` and `arxiv_paper_embeddings`, keyed by paper, model, and abstract content hash.
- This independent experimental mode does not yet filter historical recommendations or negative feedback.
- Each non-dry-run command prints a `Ranking run id` that can be passed directly to module 6.

Preview the exact profile text used for ranking:

```bash
python -m agents.ranker_agent --preview-profile-text
```

## Module 6 LLM Reranking

First save a module 5 rough-ranking run, then rerank that stored batch into final explained recommendations:

```bash
python -m agents.ranker_agent --ranking-mode library --candidate-limit 200 --top-n 20
# Replace 3 with the Ranking run id printed by the previous command.
python -m llm.client --ranking-run-id 3 --top-k 5 --dry-run
```

Expected behavior:

- Module 6 consumes the specified existing `ranking_runs` batch and its `local_rankings`; it does not execute module 5 again. Omit `--ranking-run-id` to consume the most recently saved run.
- Either a `profile` run or a `library` run can be passed to the same LLM reranker.
- The LLM receives only the compressed research summary, interest keywords, and candidate paper metadata; it does not receive the full Zotero library.
- With valid LLM configuration, it returns structured recommendation cards with a rerank score, one-sentence summary, recommendation reason, related interests, and reading priority.
- Without credentials, an unavailable LLM, or invalid JSON output, the command returns local Top K fallback recommendations.
- Remove `--dry-run` to save final user-facing recommendation cards in `recommendations`, linked to their source `ranking_run_id`; module 5 rough-ranking records remain isolated in `local_rankings`.

## Module 7 Daily Recommendation Workflow

Run the full daily agent workflow:

```bash
python -m workflows.daily_recommendation_workflow
```

The workflow runs these steps with clear START/OK/SKIPPED/STOP logs:

1. Initialize SQLite.
2. Sync Zotero library papers.
3. Build a user profile.
4. Collect recent arXiv candidates.
5. Run local rough ranking and save a `ranking_runs` batch.
6. Run LLM reranking from that saved batch and save final recommendations.

Useful local-cache test command:

```bash
python -m workflows.daily_recommendation_workflow \
  --skip-zotero \
  --skip-arxiv \
  --profile-mode local \
  --ranking-mode library \
  --embedding-backend hashing \
  --dry-run
```

Common options:

- `--ranking-mode profile|library`: choose the module 5 rough-ranking method.
- `--profile-mode local|hybrid|llm`: choose the profile-building method.
- `--local-top-n 20 --final-top-k 5`: control rough-ranking and final recommendation counts.
- `--skip-zotero` or `--skip-arxiv`: reuse local cached data if a remote service is unavailable or rate-limited.
- `--dry-run`: generate and print recommendations without saving final rows to `recommendations`.

The workflow continues with local cached Zotero/arXiv data when remote sync fails and enough local data already exists. It stops with a clear message when a critical prerequisite is missing.
